# 停住 JTAG 时钟后复位：一笔 DMI 写究竟有没有执行？

归档的四路 BOOM 布线报告有两条方向相反的调试接口 `CDC-10 Critical`：一条到 JTCK 侧请求队列的清零脚，另一条到 CPU 侧响应队列的清零脚。核对原版与在综合的改版，两处复位逻辑相同。在 Vivado 2024.2 XSim 中，直接从 DMI 请求/响应口写调试模块的 `DATA0`，在两个不同时间点停住 JTCK，但继续运行 CPU 时钟：

| 停钟时，中间这笔写到了哪里 | 停钟后施加 800 ps 公共复位 | 停钟但不复位（对照） |
|---|---|---|
| 已进请求队列，CPU 侧尚未接收 | CPU 侧未接收这笔写，调试端未收到应答 | CPU 侧接收并写入一次，恢复 JTCK 后应答一次 |
| `DATA0` 已更新，响应在等待调试端接收 | 已观察到写入，但这笔应答没有到达调试端 | 不会重复执行，恢复 JTCK 后应答一次 |

四组时钟参数各跑上述四种情形，共 **16/16**。施加复位的八组中，JTCK 停止时两端同步链都清零；恢复后先经过 3 个 JTCK 上升沿，再经过 3 个 CPU 上升沿才解除联合清零。两条有效位链随后分别在本地时钟的 3 个上升沿变为 `001 → 011 → 111`。所有组都完成了后续新写并读回 `0x52e4c786`，再观察 64 个 JTCK 上升沿未见重复应答。删除请求侧对远端复位的清零、翻转后续新写的一个数据位，这两项独立负控分别触发了预期的断言。

**调试端没收到应答，不能据此判断先前的写没有执行。** 若在途遇到板级复位，先重新同步并激活调试模块；能读回的目标先读回，不盲目重发有副作用的写。这里观测的是调试模块的 `DATA0`，不是 DDR 写入，也没有验证复位前的值能保持。

[逐例计数、清零端点和来源指纹](perf-mega175-dmi-reset.json)；[测试夹具](../tests/mega_dmi_reset.sv)与[执行脚本](../scripts/test-mega-dmi-reset.py)。脚本核对两份完整输入清单、归档 CDC 报告的两行端点与上层接线，仿真 33 个未修改的 RTL 文件。持有对应构建原件时，以下命令在独立的新目录输出记录：

```sh
python scripts/test-mega-dmi-reset.py "$ARCHIVED_KIT" "$CANDIDATE_KIT" "$ARCHIVED_CDC_REPORT" "$VIVADO_INSTALL" "$FRESH_OUTPUT_DIRECTORY"
```

范围限于给定时钟参数及公共复位，不覆盖串行 TAP、任意独立复位、亚稳态或实现后异步清零的恢复/撤除时序。两条 Critical **均未豁免**；这不产生 CoreMark 成绩或上板许可。
