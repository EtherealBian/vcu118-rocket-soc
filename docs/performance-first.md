# VCU118 性能主线：先做快一个 hart

验收指标只有一个：在 VCU118 上启动 Linux，以一个上下文运行标准 2 kB CoreMark，三次性能种子**每次**达到 1,000 次/秒；另三次验证种子与 CRC 通过。多核并发另报总吞吐。旧版 [100 MHz 单核 Rocket 实板记录](coremark-1000-board.json)中，最佳配置中位数为 246.655 次/秒。继续在同一块板、同一 100 MHz bitstream 上测试，GCC 15.1、`-O3 -flto`、Zba/Zbb 已把中位数提高到 **254.232**。距目标还需 3.93 倍。[新一轮实板记录](coremark-1000-compilers-board.json)与新核的进度分开报告。

| 配置 | 本轮要回答的问题 | 时钟和结果的边界 |
|---|---|---|
| 单核 Rocket，顺序单发射 | 只换编译器、LTO 或循环展开，实板速度会变多少？ | 使用已验证的 100 MHz 系统；同一次 Linux 启动交错测量 |
| 单核 BOOM v3 Medium，双路 | 在不改变 ELF 时，乱序执行能省多少周期？ | 原版 100 MHz 整机布线时序达标，但调试停核 CDC 未通过审查，未上板；修订版须重新实现 |
| **单核 BOOM v3 Large，三路译码/提交，96 项 ROB** | 和双路相比，省下的周期能否抵消更宽设计的频率损失？ | 同一 `-O3` ELF 在 100 MHz 对照 RTL 中的六个窗口均比双路快；175 MHz 候选 RTL 已生成并核对三路/96 项 ROB；尚无该频率的整机布线签核。175 MHz 不是已实现频率 |
| 单核 BOOM v3 Mega，四路译码/提交，128 项 ROB | 同一 ELF 能否进一步减少周期？ | 12/12 个裸机 RTL 窗口进入 175,000 周期预算；没有四路布线频率或 Linux 板测分数 |
| 四核九级 Rocket | 九级短路径是否正确？多核 Linux 和共享内存是否正确？ | [SMP 与九级验证](quad-nine.md)独立推进，不把总吞吐计为单核成绩 |

## 为什么从三路开始

在[同一 `rv64gc` ELF 的裸机热区](coremark-1000-rtl.json)中，性能种子每轮退休 358,881.75 条指令。单发射 Rocket 用 445,246.5 周期，双路 BOOM 用 223,562 周期。若这个窗口要在 **175 MHz** 达到每秒 1,000 轮，预算是 **175,000 周期/轮**：双路的周期数还须下降 **21.72%**，且平均须退休 **2.051 条/拍**，超过两路提交的理论上限。改进编译器可能减少指令数，所以软件对照也保留。这是 M 模式行为内存窗口的预算，不是 Linux 分数预测。

换成第二份通用 `rv64gc -O3` ELF 后，两颗核在性能种子每轮均退休 344,107.25 条指令。Rocket 用 **439,168.5** 周期，双路 BOOM 用 **226,170.25** 周期；验证种子分别为 441,272 和 228,018.5 周期。[两种子的原始计数及 ELF 身份](coremark-1000-rtl-o3.json)。相对各自 `-O2`，指令少 4.12%，Rocket 周期少 1.37%，双路 BOOM 却多用 1.17%。因此按每轮时间选编译配置，不能只看指令数量或选项等级。

### 双路与三路：同一程序的实际差距

| `-O3`，两次比较均用同一份 ELF | 双路周期/轮 | 三路周期/轮 | 周期降幅 | 双路 → 三路 IPC |
|---|---:|---:|---:|---:|
| 性能种子，三次中位数 | 226,170.25 | **178,976** | 20.87% | 1.521 → 1.923 |
| 验证种子，三次中位数 | 228,018.5 | **179,914.25** | 21.10% | 1.512 → 1.916 |

[逐次周期、退休数和 ELF 哈希](perf-wide-o3.json)。每个窗口四轮；同种子的退休指令数逐次相同，三路在六对窗口中全部领先。三路和双路也有缓存、预测器及发射组织的差别，不能把收益全部归因于多一路提交。以性能种子计，如果三路布线后的工作频率低于双路的 79.13%，这个周期优势就不够。按 175,000 周期/轮筛选，**六个窗口都没有通过**；性能中位差 3,976 周期，验证中位差 4,914.25 周期。均非 Linux 实板成绩。

换成通用 `-O2` 后，严格按 ELF 哈希给双路重跑：性能种子 **223,562 → 177,191.75 周期/轮**（−20.74%，IPC 1.605 → 2.025），验证种子 224,820.25 → 178,005（−20.82%）。[独立的六对采样](perf-wide-o2.json)也全部更快，但仍无一个三路窗口进入预算；较好的 `-O2` 性能中位仍差 **2,191.75 拍**。第一次对照虽有相同裸机载荷，却因 ELF 不同被拒；本表用的是重跑后的配对数据。

选择实现按 `通过时序且经核对的时钟频率 / 每轮周期数` 比较：三路若只用双路周期数的 85%，它的时钟就必须**高于**双路的 85% 才能更快。先用同一二进制比较两套种子，再审查整机时序、CDC、DRC、时钟、管脚及 ROM；过关才通过 JTAG 易失配置，最后以 Linux 板测为准。若新增一个核能提高并发吞吐但降低单核频率，报告两项，不用核数弥补单核差距。

**为什么不固定流水级数？** Celio 等在 [BOOM v2 的物理设计报告（UC Berkeley，2017）](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2017/EECS-2017-157.html)中记录过：换代后，每拍完成的指令数最多下降约 20%，作者将主要损失归因于加载到依赖指令的延迟增加。这不是 VCU118 的测量，但给出了具体的检查点：若为布线多加一级，必须用依赖加载链和同 ELF 热区复测它是否真的省时间。BOOM 团队[公开的另一 FPGA 实现](https://boom-core.org/)是 EC2 F1 上的 FireSim 流程，不能用它或 ASIC 时钟为本板 175 MHz 签核。

## 复现实验

- 三路配置来自锁定的 [BOOM v3 `WithNLargeBooms`](https://github.com/riscv-boom/riscv-boom/blob/d2a64f7ca9fd914d9c686cb23edcd32d3465a02e/src/main/scala/v3/common/config-mixins.scala)：TAGE-L 预测器，整数/访存/浮点发射队列分别最多 3/1/1 路。不是任何三条指令都能同时发射。对比 [SonicBOOM 论文和另外两个开源内核](quad-nine.md#谁做到了什么)时，引用值都不作为本板数据。
- WSL 按 [bring-up](bring-up.md)准备工具。依次运行 `bash scripts/generate-perf-boom.sh`（双路）、`bash scripts/generate-perf-wide.sh control`（三路 100 MHz）；对同一窗口用 `scripts/compare-cpu-window.py` 复核两份模型、ELF、阶段计数及逐轮退休数。不要并行改写同一 Chipyard 生成目录。三路周期有收益，再运行 `bash scripts/generate-perf-wide.sh perf175`；该目标使用独立的类、生成目录、ROM 与时间基准。
- `scripts/check-boom-shape.py` 从 ChipTop 逐层定位唯一 BOOM 核，在生成的 RTL 里数译码单元、检查 ROB 各提交端口、各 bank 的有效位及驱动。100 MHz Large 的[生成结构与 RTL 摘要](perf-large-structure.json)已核对：1 个 hart、3 个译码单元、3 路提交、3 × 32 个有效项。设备树、ROM 字节和板级 PLL 请求亦通过静态检查。它不测持续 IPC，也不认定 BOOM 是九级。
- 编译器实验镜像：`VCU_COREMARK_COMPILERS=1 VCU_COREMARK_AB=1 bash scripts/build-lab-linux.sh "$HOME/.cache/vcu118-build/compiler-test" artifacts/compiler-test`。先打包、验证镜像并启动。已评审的 100 MHz Rocket 上，用 `test-board-coremark-matrix.ps1 -Experiment compilers`（其余参数见[实板步骤](coremark-1000.md)），交错比较 GCC 13.3 的 `-O3 + Zba/Zbb`、GCC 15.1 的 `-O3 + LTO + Zba/Zbb` 与 GCC 13.3 的 `-O3 + LTO + unroll + Zba/Zbb`。每种配置三次、每次两套种子各 12,000 轮；复核 SHA、版本、flags、Linux 报告的 ISA 扩展、CRC 和主机墙钟。固定同一份对照 ELF。编译器和编译选项组合的差值不能归因于其中的某一项。

### 定位瓶颈，而不是猜

`bash scripts/build-cpu-window.sh <新目录> boom-events` 构建独立的 M 模式诊断程序；运行 `scripts/run-cpu-window.sh` 时在五个常规参数后加 `--boom-events`。只接受带匹配配置的 BOOM v3 Medium 模型，读回五个硬件事件选择器。报告分支误预测、间接跳转误预测、ROB 清空、L1 指令/数据缓存 acquire 的事件周期数及每千条退休指令的中位数。它们不能直接相加为停顿，也不提供“分支预测命中率”的分母。带计数器的 ELF 不参与上述同 ELF 架构比较。

双路的两次独立计数器实验已完成：[GCC 13.3 `-O2`](perf-medium-events.json) 与 [`-O3`](perf-medium-events-o3.json)。性能种子的分支误预测事件周期/千条退休指令分别为 1.202 与 1.258；`-O2` 后两个性能窗口的 I$/D$ acquire 均为零。这只描述这些热窗口，不证明扩大缓存没有价值，也不等于误预测率。

175 MHz 的串口链路须两端匹配。[100 MHz 引脚对照](rom-link-100-control.json)已测到首字节 9 个相邻跳变均为 868 拍；误设为 175 MHz（1,519 拍）时按预期拒绝。20 字节错误 CRC 帧停在 ROM，64 字节正确帧经 ROM 交给载荷并收到 `K`。这次测试模拟外部存储器；不能替代板上 UART 或 DDR。现有 100 MHz 诊断程序会重写 UART 分频，旧模拟器也按 100 MHz 接收；不能只替换 PLL、复用旧模拟器或固件，就把输出算作 175 MHz 的验证。Linux 板测仍须检查匹配的时钟设备树、独立的时基和主机墙钟。

**二进制复现说明。** 两个全新目录独立重建默认 `-O2` 窗口后，裸机载荷保持既有的 `2d2525c7…`，两份 ELF 逐字节相同（`ca2072e2…`）。早期 GCC 为入口汇编产生随机的临时对象文件名，导致其名字留在 ELF 符号表中，现已改为固定 `entry.o`。历史对照使用各自封存的原 ELF，不倒改旧哈希。

### 新核的 Linux 软件对照

三路候选报告的 ISA 不含 Zba/Zbb，不能直接部署 Rocket 上得分最高的二进制。用 `VCU_COREMARK_AB=portable bash scripts/build-lab-linux.sh <新构建目录> <新产物目录>` 可构建三份标准 RV64GC 用户程序（GCC 13.3 `-O2` / `-O3`、GCC 15.1 `-O3 -flto`）。新镜像已在 QEMU 单核 Linux 启动并验证 GCC 15.1 版本的两套种子与 CRC；同一模拟器、同一 CPU 型号另测普通 `addi` 正常，`sh1add` 和 `andn` 分别触发非法指令陷阱。[固件、ELF、ISA 与 CRC 记录](portable-linux-qemu.json)不含 QEMU 性能数字，不代替新核板测。

```bash
python3 scripts/test-coremark-qemu.py <产物>/fw_payload.bin <产物>/coremark-g15-gc-lto.elf logs/qemu-portable-new --profile g15-gc-lto
```

### 175 MHz 改了哪些逻辑？

将两套封存的生成输入[逐文件核对](perf175-hdl-delta.json)：535 份 HDL 中，映射配置类文件名后，531 份逐字节相同（含 BOOM 核和存储器模型），源顺序相同。其余四份是 ROM/DT、UART 复位分频、复位去抖逻辑与其 14 → 15 位计数器。最初“只会变 ROM”的假设被文件比较否定；报告检查其余三份的精确文本差异，ROM 内容用独立 DT/引脚测试核验。**生成的 PLL 请求不是板上频率。**

### 同一程序，三路和四路各用多少拍？

单核四路 BOOM v3 Mega（`bash scripts/generate-perf-wide.sh mega`）的[生成结构](perf-mega-structure.json)是 4 路译码、4 路架构提交、4 × 32 个 ROB 项。它是**一个**物理核的设计，与四核九级 Rocket 无关。表中每格是三个裸机 RTL 窗口的中位数，单位为周期/轮；相邻两列比较的是同一 ELF、同一 ROM、相同的退休指令数。

| 编译配置与种子 | 三路 Large | 四路 Mega | 四路少用周期 |
|---|---:|---:|---:|
| [`-O2` 性能](perf-mega-o2.json) | 177,191.75 | **162,125.50** | 8.50% |
| `-O2` 验证 | 178,005.00 | 162,806.00 | 8.54% |
| [`-O3` 性能](perf-mega-o3.json) | 178,976.00 | **164,276.75** | 8.21% |
| `-O3` 验证 | 179,914.25 | 165,377.50 | 8.08% |

**12/12 个四路窗口都比三路快，也都在 175,000 周期/轮以内，最慢 167,114。** 这是第一次有候选完全通过这个筛选门槛。四路还改变了访存发射等结构，不能把收益全部归给宽度。按 `-O2` 性能种子，四路要保住三路时钟的 **91.50% 以上**才有净收益。175 MHz 是算预算时的假设，不是实现频率；外存模型也不是物理 DDR。没有以这些数字推算 Linux 分数。

三路另做两次软件对照：以通用 GCC 13.3 `-O2` 为基准，[函数/循环对齐 32/16 字节](perf-wide-software-o2-align.json)的性能中位数反而多用 2.2023% 周期；[通用 GCC 15.1 `-O3 -flto`](perf-wide-software-g15-lto.json)多用 0.4096%。这两项都没有作为对三路的加速发布。

### 时序和上板分开验收

* **双路 100 MHz：[原版的布线、资源和 CDC 摘要](perf-medium-route.json)**。224,292 条网全部布通，零布线错误；全设计 setup / hold / pulse-width 最小余量分别为 +0.430 / +0.012 / +0.143 ns。149,525 个 LUT、91,143 个寄存器、174.5 块 BRAM、64 个 DSP。579 条 CDC 记录中有 7 条 Critical，其中一条是 JTCK 停核请求经过组合逻辑到核域同步器，另有一条到复位预置端的记录尚未分类。**没有将这个 bit 配置到实板。**
* 修订版将远端停核电平先过两级同步器，再与本域延迟两拍的停核电平合并；只接受完整哈希匹配的 Medium 调试图。原版和修订版的 `TLDebugModule` 均跑了 9 个 JTAG 时钟/相位组合，每组 16 次 DMI 操作。110,205 个逐拍观察通过两拍等价检查，其中 536 个能实际观察到延迟差。新候选归档 `97103832979270e40209c8808175e4561252e48ab6fa2e893f6733a6422300e1`，**不能继承原版时序**。修订版仍须重新审查布线、停核结构、异步队列、复位和管脚。
* **三路 175 MHz：[优化后、布局前的端点报告](perf175-path-estimate.json)**。原实现止于布局后的物理优化，没有最终布线报告或 bit。重新打开保存的 `post_opt` 检查点：系统时钟最差的 40 个不同 setup 端点都从同一个 D-cache tag-match 寄存器发起。最差路径经过 MSHR 响应队列，到整数发射单元的 dispatch-ready；38 级逻辑，估算数据路径 9.918 ns（逻辑 1.636、估算连线 8.282），要求 5.714 ns，余量 −4.414 ns。这是**布线前估算，不是 Fmax**。可用 `scripts/diagnose-routed.tcl` 中的 `vcu_endpoint_reports` 从已打开的检查点导出，再用 `scripts/review-preplace-path.py <报告目录>` 核对阶段、时钟和端点。
* **175 MHz ROM/UART**：[独立引脚测试](rom-link-175.json)实测 9 个连续边沿间隔均为 1,519 个模型时钟，故意用 868 拍解码会被拒绝；20 字节 CRC 错帧停在 ROM，64 字节正确帧交接到载荷。这不是物理串口波特率、PLL 或完整 Linux 实板验收。

### 发射队列末段：分组计数是否划算？

抽取四路 Mega 的 40 槽整数发射队列，用相同已注册输入与输出，只比较「40 个槽可用位 → 4 路 dispatch 信用」：原版注册阈值结果，候选版每四槽注册一个部分计数，下一段做总和与阈值判断。它不包含产生槽可用位的 D-cache/MSHR 路径，也不模拟下游扇出。

| 5.714 ns 约束，VU9P 独立布线 | setup 余量 | hold 余量 | 最差数据路径 | LUT / FF |
|---|---:|---:|---:|---:|
| 原版计数 | +3.943 ns | +0.060 ns | 1.752 ns | 42 / 48 |
| 每四槽注册部分计数 | +4.187 ns | +0.053 ns | 1.507 ns | 50 / 74 |

两版都布通；210,701 个可观察周期中，两组输出均与独立软件计数器逐拍相同。测试涵盖 0–40 的所有置位数，以及所有至多 3 个置位的位置组合。这个切片用 **8 个 LUT 和 26 个 FF** 换到 **0.244 ns** 的最差 setup 余量，hold 余量略少。值得做整核对照，但不能把局部余量加到整核时序上，也不能由此宣称达到 175 MHz。[两组布线摘要与测试输入哈希](perf-issue-slice.json)。

复现：`issue-ready-fixture.py <锁定的四路 IssueUnitCollapsing_2.sv> <新目录>` 提取测试输入；运行 `bash scripts/test-issue-slice.sh <同一目录> <新模型目录>` 保存 stdout。用 Vivado 2024.2 执行 `-mode batch -log <同一目录>/vivado.log -source scripts/route-issue-slice.tcl -tclargs <同一目录>`，再以 `review-issue-slice.py <同一目录> <锁定的 HDL> <模型 stdout>` 交叉核对。生成的 HDL 和原始工具报告留在本地。

两套种子的最终 CRC 分别为 `0xd340` 和 `0xbc68`；18 次主机墙钟范围 52.612–55.659 秒，与客机计时最大绝对差 0.094 秒。通用软件最快中位数为 **228.241023**。此前 Rocket 上使用 Zba/Zbb 的[最快实板中位数 254.231902](coremark-1000-compilers-board.json)仍未被超过；它是另一份程序，不能作为三路/四路 BOOM 的同 ELF 对照。单核 1,000 的目标尚未达到。

### 单核四路 BOOM：上板前的调试中断验证

四路 BOOM 与双路的 TileLink 标签、tile 和 CSR 不同，不能直接沿用双路的调试验证。沿 JTAG 停机请求和本地复位停机请求重新检查了两条来源，直到四路核心的 CSR；锁定对应的完整模块哈希。在独立的 **100 MHz 设计配置**功能模型里，两条请求先各自寄存，再合并，原有的 tile 端接收同步链保留。原版和修订版的真实 `TLDebugModule` 各跑 9 种时钟半周期/相位组合，每种 16 次 DMI 事务。**110,205 次观察**均符合预期的两个目标时钟边沿延迟，其中 536 次能区分新旧输出。独立复核从原版重新派生相同修订版，然后重放两份可执行模型，逐字节核对输出和完整轨迹。[输入身份与复核结果](perf-mega-halt.json)。

复现：用 `derive-mega-halt-model.py <四路原始功能包> <新功能包>`，对两个包分别设置 `VCU_SIM_KIT` 运行 `bash scripts/test-debug-halt-sources.sh <各自全新输出>`，再执行 `python3 scripts/review-mega-halt.py <原包> <新包> <原输出> <新输出>`。这是调试模块的功能等价实验，不能证明 FPGA 亚稳态、复位/DDR 跨域收敛或四路整机时序，也不是 Linux 实板成绩。

### 四路发射队列：调整寄存器位置，不增加派发等待

四路 BOOM 原先先数出整队列的可用槽，再寄存四个派发许可。新配置在同一个时钟边沿分别寄存每四个槽的可用数，下一级再相加并判断能否接收第 1 至第 4 条指令。目的是缩短送入寄存器的长路径；代价是寄存器之后的路径变长，所以收益必须由整机布线判断。

比较两次 Chisel 生成的 548 项有序 HDL 输入：545 项内容逐字节相同，只有 24、32、40 槽三个发射队列改变。分别有 6、8、10 组部分计数。对每个模块抽取实际加法、位宽、截位、寄存器和门限；确认每个槽的可用谓词相同，扣除抽取部分与对应仿真随机初值赋值后，其余模块文本按空白归一化相同。让 Yosys SAT 自由选择所有槽的可用位，证明第一个时钟沿之后，两版四路许可全部相同。两版都只依赖上一拍输入，没有更早状态；40 槽的一个证明覆盖 `2^40` 种输入。故意让候选漏计最后一个槽，三个队列都得到可按位复算的反例。[三组证明、反例和源文件哈希](perf-real-issue-proof.json)。这不证明首次时钟沿之前的值、整核最高频率或 Linux 分数。

复现：依次运行 `bash scripts/generate-perf-wide.sh mega` 和 `bash scripts/generate-perf-wide.sh partial-mega`；将两次生成目录各自的 `gen-collateral` 按先原后新传给 `python3 scripts/prove-issue-credits.py <原目录> <新目录> <全新本地输出目录> --yosys <Yosys 可执行文件>`。成功时会生成 `proof.json`；源码、反例与输入摘要可公开，提取的网表和原始日志不随仓库分发。

### 板级串口接收：验证的是哪一段？

ChipTop 引脚仿真不包含 VCU118 的外层串口接线。用 Vivado 2024.2 xsim 直接驱动外壳的 `uart_rxd`，保留原始板级顶层（修订组仅应用锁定补丁）和真实引脚转换器，在 `ChipTop.uart_0_rxd` 处观测。原版零拍直通，修订版经两级寄存器。在 5,000 ps、2,857 ps 两种接收时钟半周期下，两版各做 1,025 次检查，每组有 517 次能区分零拍与两拍；四个错误延迟负控均抓到了不匹配。[引脚仿真摘要](perf-physical-rx.json)。在全新目录重新生成双路修订包，548 个清单条目与重构脚本前逐字节一致。CPU、DDR、PLL 均未纳入本次 xsim 测试；亚稳态、物理时序和实板串口须单独验收。

复现：在 Windows 运行 `python scripts/test-shell-rx.py <未修改板级封装的私有实现输入目录> <全新本地输出目录> <Vivado-bin目录>`。测试既要求正确路径通过，也要求错误延迟确实被拒绝。

### 三路 175 MHz：慢在哪里，先改哪一段？

三路 BOOM **优化后、未布局**的最慢 8 条详细 setup 路径，都从数据缓存第 0 路标签匹配寄存器出发。对每条报告从发射寄存器的 C 到捕获寄存器的 D 逐项解析：8 条路径先共用 25 个组合单元；抵达第一个名字属于发射队列的组合原语输入时，均已过 26 级，耗时估算 **7.062–7.072 ns**，而 175 MHz 每拍只有 **5.714 ns**。再到 3 个派发许可寄存器还需 2.632–2.846 ns；另 5 条落在队列槽位的操作数状态，而非许可计数。这里只按映射后的引脚划界，不将层次名当作源码流水级，也不把估算当作布线延迟。[逐路径分解和报告哈希](perf175-path-prefix.json)，可用 `python3 scripts/review-path-prefix.py <同一份 max timing 报告>` 重算。

两种办法分开评估：

- **不采用全面关闭提前唤醒作为默认值。** 三路核关掉 speculative load wakeup 后，生成网表的 3 个相关接口消失，普通整数加载结果仍送回核心。[生成接口复核](perf-large-no-fast-structure.json)。用相同 GCC 13.3 `-O2` ELF 在两套整核 RTL 上比较对应窗口（每个窗口 4 轮）：性能种子中位数由 177,191.75 增至 **189,201.75 周期/轮**，验证由 178,005 增至 **189,856.25**。6 个窗口全部变慢，退休指令数逐对一致。按这些窗口的表现，主频至少提高约 **6.78%** 才能抵消性能种子的周期代价；还没有物理时钟依据。[6 对窗口与输入哈希](perf-large-no-fast-o2.json)。复现：以 `control` 和 `no-fast-load` 生成两个模型，用同份 `-O2` 负载完成 `run-cpu-window.sh`，以 `screen-core-windows.py <原输出> <原包> <新输出> <新包> <负载> --same-organization` 复核。
- **新增 `early-way` 单变量候选。** 在一级缓存中，把送给缺失状态寄存器（MSHR）的“标签命中就用命中路，否则用替换路”选择移到**已有的** S1→S2 边界前寄存。原始 8 位路掩码保留，不把多位置位的输入折成单一路号；普通加载命中、重放、分支取消以及握手接口不改。代价可能是 S1 更长；即便这条路缩短，标签状态和其他扇出仍可能限频。**暂不计为性能改善**。用 `bash scripts/generate-perf-wide.sh early-way` 生成，`VCU_BOOM_MODEL=early-way` 走独立模型目录；先与 `control` 同 ELF 比周期和退休数，再比较完整实现。

### 旧双路 BOOM 的未分类复位路径

在**原版双路**的同次布线输出中，重新找到 CDC 报告的两个 `CDC-7` 起点：DDR 控制器组 0 的复位寄存器和上电复位寄存器。不是凭端点近似命名归类：从 SDF 的 `INTERCONNECT` 反查到具体的 LUT4，再与同时导出的时序网表比对输入和 LUT 真值表。4 个输入为 PLL 锁定、外部复位、DDR 复位和上电复位；16 种输入组合均与“未锁定或任一复位有效”一致。LUT 输出进入消毛刺寄存器的异步 preset；该寄存器 Q 恰好连接两个时钟域内共 6 个异步 clear，每域 3 个寄存器、两条 Q→D 级间连接。[布线连接、真值表和五项产物哈希](perf-medium-reset-trace.json)。复现：`python3 scripts/trace-medium-reset.py <原双路布线输出的 obj 目录>`。

这只解释了这两条报告路径**实际连到哪里**，不证明无毛刺、亚稳态安全或恢复/撤销时间，不修改 CDC 豁免。原版调试中断的问题仍在；修订版需要用自己的布线重新检查，不能凭此上板。

### 同一单核四路 BOOM：哪种程序先拿去上板？

在相同的四路整核 RTL 和行为内存上，GCC 15.1 `-O3 -flto` 的性能种子比 GCC 13.3 `-O2` **少退休 5.8792% 的指令，却多用 2.2308% 的周期**。以下均为三个裸机窗口的中位数，每个窗口四轮，不是 Linux 计时得分。

| 每轮周期（越小越好） | 三路，GCC 15.1 `-O3 -flto` | 四路，同一份 GCC 15.1 ELF | 四路，GCC 13.3 `-O2` |
|---|---:|---:|---:|
| 性能种子 | 177,917.50 | 165,742.25 | **162,125.50** |
| 验证种子 | 178,305.50 | 166,299.00 | **162,806.00** |

横向先看前两列：相同程序在四路上每轮少用 **6.8432% / 6.7337%** 的周期，各种子的三个窗口都更快。两种硬件的队列、缓存等组织也有差异，不能把收益全归给发射宽度。[同 ELF 的逐窗口比较](perf-mega-g15gc-hardware.json)。后两列才是同一硬件上的软件比较：[六对窗口、退休数量与程序哈希](perf-mega-g15gc-software.json)。因此四路首轮 Linux 板测应保留 GCC 13.3 `-O2` 对照，并与通用 GCC 15.1 程序同板交错测试。本表裸机诊断编译为 `-march=rv64imac_zicsr -mabi=lp64`；前述实板通用程序是 `rv64gc/lp64d` 的 Linux ELF，不能混为同一二进制。

为测试四路在更高频率下能否工作，新增单 hart、四路、128 项 ROB 的 **175 MHz 请求配置**。对照 100 MHz 四路原版，548 个有序 HDL 输入中 **544 个逐字节相同**。改变的是启动 ROM、UART 分频、复位延时及其计数器（14 位变为 15 位）；处理器 RTL 未变。[逐文件时钟差异记录](perf-mega175-clock-delta.json)。频率请求不代表已达到的 FPGA 主频。

复现：以 `bash scripts/build-cpu-window.sh <新目录> control` 构建 GCC 13.3 诊断程序，另以 `VCU_WINDOW_CC=15 bash scripts/build-cpu-window.sh <另一新目录> o3-lto` 构建 GCC 15.1 程序。在三个硬件/程序组合分别执行 `run-cpu-window.sh`，用 `screen-core-windows.py` 比同一 ELF、`compare-window-software.py` 比同一硬件。四路时钟对照用 `bash scripts/generate-mega175.sh <新的175MHz模型包> <封存的100MHz四路模型包>`，再用 `python3 scripts/check-wide-clock-delta.py <100MHz包> <175MHz包> --family Mega` 复核。

四路 175 MHz 原版模型还单独测试了真实 ROM 的 UART 引脚。主机没有预装模拟 RAM：64 字节正确帧在第 **1,491,491** 个模拟周期收到交接标志和小程序回复 `K`；20 字节坏 CRC 帧在第 **823,132** 个模拟周期确认停机提示及静默窗口。两项均检查 20 个比特时间的空闲。首字节 9 个边沿间距均符合每位 **1,519 拍**；用 100 MHz 对应的 868 拍解码被负控拒绝。[原版串口引脚测试与输入哈希](perf-mega175-rom-link.json)。复现：`bash scripts/test-clocked-rom-link.sh <175MHz四路包> <匹配的模型对象目录> 175 single <新输出目录>`，再运行 `python3 scripts/review-clocked-rom-link.py <输出目录> <同一模型包> 175 single`。这些测试不含板级 PLL、DDR PHY 或 Linux，也不能替代修订版自己的串口测试。
