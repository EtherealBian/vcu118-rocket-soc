# 外部读响应多等 32 拍，四路 BOOM 的热区多花多少拍？

性能种子四轮共从 **653,447 拍增至 660,479 拍（+7,032，+1.08%）**。其中 6,037 拍的净增量发生在第一轮，第四轮反而少 63 拍。这是同一个四路 BOOM RTL、同一份 Linux 用户态快照下的对照，单位是**模型周期**，不是板测分数。

| 种子 / 外部 Get 首个响应时刻 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 第 4 轮 | 四轮合计 |
|---|---:|---:|---:|---:|---:|
| 性能 / A+1 | 171,404 | 161,746 | 160,691 | 159,606 | 653,447 |
| 性能 / A+33 | 177,441 | 162,665 | 160,830 | 159,543 | 660,479 |
| 性能 / 差值 | +6,037 | +919 | +139 | -63 | +7,032 |
| 验证 / A+1 | 173,150 | 162,949 | 161,180 | 160,257 | 657,536 |
| 验证 / A+33 | 178,528 | 163,428 | 161,287 | 160,045 | 663,288 |
| 验证 / 差值 | +5,378 | +479 | +107 | -212 | +5,752 |

**与 1,000 次/秒的关系。** 即使按请求的 175 MHz 算，每轮也只有 175,000 拍。加 32 拍后，性能首轮超出 2,441 拍；四轮平均仍低于预算 9,880.25 拍。单轮超出不足以断定长跑失败，四轮平均低于预算也不足以断定达标。这个样本说明首轮对外部读延迟敏感，但不足以支持先改 DDR 控制器或扩大缓存；主线仍先看同一构建的最终时序和重复慢路径。

**为什么不能用读请求数乘以 32？** 加延迟时，性能四轮在外部口新接受的 Get 是 `218 / 20 / 1 / 1` 笔，实际落在各轮里的“应答尚未允许出现”是 `6,947 / 645 / 56 / 20` 拍；它们与表中的 CPU 周期差不同。验证种子第三轮没有新 Get，却包含上轮未结束的读带来的 24 拍人为等待。这里按两次相邻轮首提交间的半开区间计数，Get 计 A 接收时刻，跨多拍写入只计最后一个 A。读仍可能跨越边界，时序变化也可能改变后续的请求和重叠；不能把某一轮负的周期差解释成慢内存提升了性能。两种种子从 MRET 到首个热区 PC 均从 229 变为 605 拍，这段不在表内。

### 测量范围

两组都只改外部 TileLink 行为 RAM 的应答：在接收 `Get` 的那个沿采样权限。若此时为 U 态，就把第一个读响应可见的时刻从 A+1 改为 A+33；32 拍中 A 口继续反压。写响应、后续读节拍、非 U 态请求都按原模型处理。**这不是给每条 load 加 32 拍**。同一个口可服务取指、数据和页表等流量，不能从 Get 次数反推 D-cache miss 数。模型一次只处理一笔请求，不含真实 MIG、DDR 排队、刷新或 Linux 中断。

两种时延各自重放同一单 hart、单上下文、2,000 字节的性能和验证快照。四次完整提交 PC 均与独立 QEMU 顺序一致；异常处理器均在核对 32 个寄存器槽、可写段、栈和堆后输出 `K`。零附加延迟的两次还与此前未插桩模型的 PC、UART 及事件文件逐字节一致。这不是在 BOOM 上完整运行 Linux 或执行 24,000 轮计分。

### 离线复现

按[已核验的快照与原版模型](perf-strict-user-replay.md#离线复核)准备输入。`INCLUDE` 为配套 Verilator 的 `include` 目录；两个私有输出目录须不存在。命令只重链原版整核归档，不重新生成 RTL，不访问 JTAG 或串口。

```sh
python3 scripts/test-strict-tl-wait.py pins "$STOCK_KIT" "$STOCK_OBJ" "$PRIVATE/pins" "$INCLUDE"
python3 scripts/test-strict-tl-wait.py replay "$STOCK_KIT" "$STOCK_OBJ" "$PRIVATE/guest" "$PRIVATE/wait" "$INCLUDE"
python3 scripts/review-strict-tl-wait.py "$PRIVATE/wait"
```

独立的引脚测试实际送了八拍写入，并在写确认和每个读节拍施加反压；U 态 Get 都在第 12 拍被接受，第一拍 D.valid 分别为 13 / 45，第一拍实际传输为 14 / 46，最后一拍为 28 / 60。另一笔非 U 态 Get 不加延迟。在测试程序的私有副本中把 `D.valid` 提前一拍，测试在引脚检查处按预期失败。另对零注入的两份真实记录各移动一个首次应答时刻一拍，事务审查均拒绝。公开[分轮结果、输入与输出摘要](perf-strict-tl-wait.json)，不公开内存快照、原始事务或板卡信息。
