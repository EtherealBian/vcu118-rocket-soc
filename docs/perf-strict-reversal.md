# 四路 BOOM 的下一次指针加载在等什么？

在原版四路 BOOM 的两个用户态 RTL 重放窗口里，链表反转循环连续两次指针加载之间，结果到结果的中位数和 P95 都是 **5 拍**。末端分支被记为忙队首的零退休沿，几乎全发生在它**已进入整数执行端口、但 ROB 忙位尚未清零**的时候。二者是不同的等待，不能把忙队首计数直接当作可省的周期。[按种子分开的直方图与指纹](perf-strict-reversal.json)。

| 同一严格对齐 ELF，单 hart，每种种子 4 轮 | 性能种子 | 验证种子 |
| --- | ---: | ---: |
| 末端分支 / 回跳 / 退出 | 24,480 / 23,664 / 816 | 24,480 / 23,664 / 816 |
| 指针值来自数据缓存 / 存储队列转发 | 24,472 / 8 | 24,472 / 8 |
| 回跳后，复制与加载在同一派发沿的相邻槽 | 16,620 | 16,735 |
| 三段间隔在同一个回跳上恰好是 2、1、2 拍 | 22,931 | 22,927 |
| 其中复制与加载又是同拍相邻派发 | 15,950 | 16,064 |
| 上次指针结果到下次结果：中位数 / P95 / 最大（拍） | 5 / 5 / 36 | 5 / 5 / 35 |
| 该分支占据忙队首且无退休：指针结果之前 / 结果至分支执行之前 / 执行至清忙之前（拍） | 0 / 5 / 27,955 | 0 / 6 / 27,686 |

**如何区分这两条路径。** 对每次回跳，比较上次加载实际返回的 64 位指针、`mv x8,x14` 在整数端口读取的第二操作数，以及下一次 `ld x14,0(x8)` 在地址生成单元读取的基址和发出的地址，四个值必须相等。三段间隔依次是上次结果到复制执行、复制执行到下次地址、下次地址到下次结果。另对每一条末端分支核对执行操作数 `(本次加载值, 0)`、下一拍注册的方向、退休后继及是否实际发出重定向。两个种子各 24,480 条分支，从执行到自身 ROB 槽首次不忙都恰好是 2 拍；这并不证明能提前 2 拍退休。

**工程含义。** 可以单独实验：如果相邻整数复制的下一条标量加载只需要复制前已有的源值，能否在重命名时让加载直接等待原生产者，同时保留复制本身的分配、写回和退休？同拍**派发**不是同拍**译码**的证明，上表也不是优化命中数。是否正确、是否缩短整段执行时间、是否损伤 FPGA 关键路径，必须分别测量。此为原版观测，不含候选加速或板测结论。

[相邻复制到加载的定向 RTL 实验](perf-copy-load-rename.md)已完成；是否缩短整核热区仍待实测。

## 复核

先取得[原版重放及重定向记录](perf-strict-redirects.md)和[同一版本的队首捕获](perf-strict-rob-heads.md)，再在全新目录重新链接只读探针。按派发沿与 ROB 槽识别动态指令，不仅按 PC；循环首轮直接进入加载，退出也不产生下一次复制。两种种子的有序退休 PC、派发/退休票据、B2、UART 与事件都与此前记录逐字节一致。把分支清忙前的区间与先前核验过的忙队首沿逐拍相交。公开结果只含聚合与指纹，不含动态地址、完整轨迹或本机路径。

```sh
python3 scripts/test-strict-load-use.py "$KIT" "$OBJ" "$GUEST" "$PREVIOUS_REDIRECT_CAPTURE" "$FRESH_DIR" "$VERILATOR_INCLUDE" --reversal
python3 scripts/review-strict-reversal.py "$FRESH_DIR" "$PREVIOUS_ROB_HEAD_CAPTURE" "$STRICT_ELF" > "$FRESH_DIR/review.json"
```
