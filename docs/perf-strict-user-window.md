# 固定 Linux ELF 的单核指令预算

这次回答的是：**冲 1,000 次/秒，目标二进制每拍至少要完成多少条指令？** 使用实际待测的静态 Linux ELF，不再借用裸机 RV64IMAC 窗口的指令数。结果是用户态指令数，不是 BOOM 周期、FPGA 时钟或 Linux 板测成绩。

| 2,000 字节、单上下文 | 性能种子 | 验证种子 |
| --- | ---: | ---: |
| 计时区间内四轮的指令总数 | 1,347,261 | 1,348,735 |
| 平均指令/轮 | 336,815.25 | 337,183.75 |
| 条件分支 | 212,745 | 213,495 |
| 加载 / 存储 | 232,874 / 61,603 | 235,048 / 61,253 |
| 四轮最终 CRC | `0x9f95` | `0x19d9` |

按性能种子这四轮的平均工作量：在 **150 MHz** 下，每轮预算 150,000 拍，需要 **2.245 条/拍**；在 **175 MHz** 下，每轮预算 175,000 拍，需要 **1.925 条/拍**。所以在 150 MHz 下，即使每拍都提交两条也不够；在 175 MHz 下，两路需要兑现约 96.2% 的理想提交能力，还没算 Linux 抢占。这是四轮样本的预算，不是 24,000 轮指令数已经测得，也不表示四路实现已达到请求频率或实际 IPC。九级 Rocket 与四路 BOOM 是不同设计。

`calc_func` 占性能窗口指令的 52.35%；条件分支占 15.79%，加载占 17.28%。这些数只说明哪里值得观察。要决定是否改预测器或访存，仍需要在当前 BOOM 上看同一代码段的分支误判和等待周期；不能把每条分支都当作一次误判，也不能把每次加载都当作一次 miss。物理实现是否改寄存器堆或发射器仍以布线后的路径为准。

## 如何核对

1. 锁定源码和 GCC 15.1.0 的实际选项，保留内嵌 flags 串、重建可带符号的同一程序。重新 strip 后必须与目标 ELF 所有字节一致（SHA-256 `61f7c4579b762f86d7d7dc93d4c385d08e50248f3dd6a8a9105fd5e88b58886a`），再从未剥离版本核验函数范围。运行的是**原始已剥离** ELF。`iterate` 已被内联进 `main`；不能在符号表里虚设一个 `iterate` 断点。
2. 使用 Ubuntu 的 QEMU 4.2.1 Linux-user，单进程模拟 RV64GC。两种标准输入分别运行四轮：两个相同的种子参数（`0x0` 或 `0x3415`），再传 `0x66 4 7 1 2000`。一遍按普通翻译块展开，另一遍强制一条指令一个翻译块；均关闭块间直接链接。不能只数翻译块次数。两遍的**有序 PC 序列** SHA-256、分轮和分类计数必须一致。软件 `clock_gettime` 的两次调用和原生 POSIX 构建的两个 CRC 均独立复核；不读取模拟器秒数当成绩。
3. 纳入起始计时返回地址 `0x106b0` 起、结束计时调用 `0x10f3a` 之前动态执行的用户指令，包含这段内的被调函数。以稳态回边目标 `0x10af0` 分轮，每轮检查两次进入 `core_bench_list`。不含内核、模拟器主机代码、初始化、时钟调用本身或结果打印。按 ELF 逐字节核对反汇编；无法识别的窗口指令、残缺翻译块或缺失时钟边界均失败。[逐轮和分类数据](perf-strict-user-window.json)。

在工程根目录使用 WSL/Linux，沿用已有 CoreMark 源码缓存与 Bootlin 交叉编译器。`qemu-riscv64` 取自 Ubuntu amd64 的 `qemu-user_4.2-3ubuntu6.30_amd64.deb`（包 SHA-256 `f4d5e577e3e9b9b62a7b69b1fe7e81f64f718efa101ee902abbce9a34622b1ca`）；可只解包到临时目录，无须系统安装。所需库可沿用原 QEMU 环境。命令只输出诊断计数，不改固件或访问板卡。

```sh
bash scripts/verify-strict-user-window.sh "$QEMU_USER" "$RELEASE/coremark-g15-gc-lto-ooo-strict.elf" > /tmp/strict-window.json
diff -u docs/perf-strict-user-window.json /tmp/strict-window.json
```
