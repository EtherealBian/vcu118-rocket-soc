# 四路 BOOM：布局后最后 0.056 ns 的变化伴随什么操作？

**先查 DDR 写地址队列的入队侧，同时保留对 CPU 执行路径的检查；不要据此改 FIFO 或放宽 CDC 约束。** 以下是同一个 175 MHz 请求、四路单 hart 实现的 *post-place* 物理优化日志，不是最终时序。最后两轮 `Critical Path Optimization` 的全设计 WNS 估计从 **−8.314 ns** 到 **−8.258 ns**。不能因此断言全设计最差端点就在 DDR，也不能把单个操作的估计变化当成可收回的时延。

| 两次相邻估计之间的操作 | 区间数 | WNS 数值变化次数 | WNS 净变化 |
| --- | ---: | ---: | ---: |
| DDR AXI4 写地址通道（AW）入队侧、单个具名动作 | 42 | 13 | +0.056 ns |
| PRCI 时钟门控或复位控制、单个具名动作 | 17 | 0 | 0.000 ns |
| 两个不同网络上的连续动作，不归因给任一网络 | 1 | 0 | 0.000 ns |

42 次涉及 42 个不同的载荷寄存器位：29 个地址位、8 个长度位、4 个 ID 位、1 个大小位。脚本在封存 RTL 中从顶层 PLL、时钟整理模块，沿 MIG 外壳追到 AW 入队模块，核对全部八个队列槽的写操作。**入队寄存器用系统时钟，而不是 DDR4 UI 时钟**；虽然它在 MIG 层级里，不能把它的同步写路径一概当作跨域路径而排除。另一方面，本次日志没指出慢的是寄存器的数据、使能还是某条出线。

作为对照，三轮 SLR Crossing 优化报告 670 个对象事件，对应 665 个不同的具名单元；其中 231 次名字位于浮点流水线。该类别的 TNS 增益为 2106.011 ns，**WNS 增益为 0.000 ns**。这是不同的计量：移动次数不能用来给 CPU 瓶颈排序，TNS 增益也不等于最慢一条路径的改善。

```sh
python3 scripts/review-mega-aw-physopt.py "$IMPLEMENTATION_LOG" "$BOARD_KIT" "$RUN"
# 有本次最终 DCP、真实端点表和详细路径后，使用同一命令追加 --routed-cpu。
```

`--routed-cpu` 除了列出各目的时钟 setup/hold 样本中这 42 个单元的发起/捕获引脚，还对 CPU 最差的八条 setup 与八条 hold 数据路径逐段比对相关网和实例名（不计时钟树、不合并同名前缀/复制单元）。重点区分入队载荷的 `D`、写使能 `CE`，以及经此处发起的数据路径；样本外、综合改名或没有精确匹配均不能算排除。没有最终报告时不输出这些结果。若最终负余量集中在其他逻辑，就改查真实慢路径，不优先改 AW 或 FPU。该检查不授权上板。
