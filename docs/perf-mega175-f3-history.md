# 四路 BOOM：取指地址要等 64 位历史比较完成吗？

旧版[完整布线路径](perf-mega175-routed-recovery.md)中，循环预测器到 I-cache 地址的建立余量为 −9.230 ns。详细路径经过预测历史位、比较逻辑和一个扇出 154 的网络，之后还有两次跨 SLR；物理网名不能单独证明每个 LUT 对应哪一行 RTL。上一次改的是[循环预测器本身](perf-mega175-loop-repair.md)。这次检查同一前端的另一段：`BoomFrontend` 如何比较 F3 的预测历史和 F1/F2 保存的历史，决定是修正取指地址还是沿用原路径。

**当前正在综合的封存物理版没有被修改。** 以下从它的 `BoomFrontend.sv` 派生，都是同周期组合改写，没有添加流水级、改预测策略或更改约束。这些实验的目的是挑选下一次局部布线的候选，不是报告 Fmax 或 Linux 跑分。

## 两种缩短等待的办法

- **历史先比较。** 一次比较基础历史，一次比较额外移入零后的历史，待分支方向确定后只选一位相等结果。之所以只有两个备选，是因为第一组有控制流重定向时，原逻辑一定忽略第二组；不存在既不忽略第二组，又因第一组的已选分支而再移入一的二态条件。实际写回的历史及方向标记仍须匹配。
- **四条一组判断方向。** 不再为了统计跳转前的分支，先把最早重定向位置编码成索引、再把索引解回掩码。一个版本在两组各自做前缀判断；另一个直接用原版已判定有效的 lane 掩码与预测方向。后一种写法不能用未屏蔽的解码结果：较早指令跳转后，有分支编码不等于这条指令仍然有效。

## 同一逻辑边界的结果

从原版和每个派生的**实际 RTL 声明**追踪 82 个输出位，包括两级历史比较、预测历史、F3 校正选择（`_GEN_133` 是 `s0_vpc` 使用的判定）、F2 清除信号、控制流索引/有效位和分支掩码。556 个二态输入位包含真实 8 路预测方向、10 个解码器输出以及取指数据、掩码与历次历史。真实的压缩指令边界、各 lane 的有效性、跳转优先级保留；F3 目标地址作为 40 位输入，不包含其产生器，也不包含 I-cache BRAM。没有对方向、解码或掩码添加 one-hot 假设。

| 写法 | 8 路预测方向 → F1 / F2 历史比较（层） | → F3 校正选择 / F2 清除（层） | 该逻辑边界内组合原语数 |
|---|---:|---:|---:|
| 原版 | 24 / 24 | 26 / 27 | 1,232 |
| 仅历史先比较 | 18 / 18 | 20 / 20 | 568 |
| 仅两组前缀 | 17 / 17 | 18 / 19 | 588 |
| **两组前缀 + 历史先比较** | **14 / 14** | **15 / 16** | 677 |
| **仅用有效 lane** | **16 / 17** | **18 / 18** | **555** |
| 有效 lane + 历史先比较 | 16 / 16 | 17 / 18 | 681 |

每个数字来自同一 Yosys/ABC `xcup` 未布局映射，层数按相应输入到输出最长组合原语链计，原语总数包括 LUT 和 MUXF，**不是**占用的 LUT 站点，也不是 ns。各输出共用逻辑；改变观察边界会改变映射，不能把这些层数从旧版整机路径中直接减去。例：最快校正候选的控制流索引有效位为 11 层，原版为 10 层。面积候选对应端点为 14 层，也有代价。

- [二态证明与全部映射](perf-mega175-f3-history.json)：五种写法均证明 82 个输出位与原版相同。四种故意错误（放开 lane 2 掩码、漏记 lane 3 非跳转分支、忽略 PC 边界、混接 F1/F2 历史）分别得到反例。
- [父模块交叉检查](perf-mega175-f3-history-parent.json)：在 Vivado 2024.2 XSim 中使用**未提取的完整父模块文本**，分别实例化原版和表中两种粗体候选。在固定时钟、子模块接口桩和受控输入上观察 3,072 组二态激励，122 位（上述 82 位加实际 `s0_vpc` 的 40 位）逐组相同，原版这些位无未知值。八个 lane 均被选中过，八种 PC 分组均出现，F1/F2 各自 64 个历史位均注入过差异。两条地址不同时，观察到 472 次选 F3、102 次选测试设定的 S2 备选。未屏蔽 lane 2 的错误版本在 44 个样本与原版不同。这里没有推进时钟，不是完整处理器或指令缓存的时序功能仿真。

**决策：保留原版、最快校正候选、最少原语候选三者作同约束物理对照。** 是否集成取决于布线后的选择、清除、索引/历史等并行端点及全局最差路径，不因局部层数下降重启现有整机实现。

## 复现

`KIT` 为 SHA-256 `ce0ef1171c7b0077282602c5c97230d03850b71c350c6c9ddcdf0b7ebcb5a456` 的物理输入包；`PROOF`、`PARENT` 为两个不存在的新目录。第一步用配套的 Yosys 0.9 和 `berkeley-abc`（后者在 PATH 中），第二步使用 Vivado 2024.2。只发布自写脚本与去敏记录，不分发生成的厂商源。


## 哪些预测方向真正影响哪些取指结果？

为了判断布线报告里的“无路径”是正常现象还是边界接错，先在原版组合电路上逐位做 SAT 查询。每次只把一条预测方向分别钉为 0 和 1，其余 555 个输入在两份电路上相同但可任意取值。8 条方向 × 82 个捕获位 = 656 对，其中 **357 对存在使输出不同的输入**，另 **299 对在这个二态逻辑边界内不依赖**。每条方向能影响的输出位数依次为 **81、80、79、78、12、11、9、7**。这里不是按网表连线计数：逻辑上不依赖，布线后仍可能有工具分析得到的物理路径；不能据此加 false path。

具体来说，前四条方向中的任意一条，都能在合适输入下影响 64 位历史的任意一位；后四条均不能影响这 64 位。**但八条方向全能影响 F1/F2 两个历史比较结果、`_GEN_133`、`f2_clear` 和 CFI 索引有效位。** 因而只看“方向 → 历史总线”的延迟会漏掉后四条方向上的瓶颈。各对结论、位序、候选与证据哈希见[寄存边界证明](perf-mega175-f3-registered.json)。

为保证三种物理实验可比，同样的 556 位输入寄存器和 82 位输出寄存器包住每个组合电路。在命名端口原版先运算再延迟两沿，与实际打包的原版、两种候选各做一次三步 SAT；任意输入、无初值假定，在前两沿填满后 82 位都一致。交换第 0/7 条预测方向、交换两个比较结果、绕过输出寄存器，各有反例。**这两层仅用于测量，未给 BOOM 增加流水级。**

预备好的 Vivado 对照逐一检查保留 556+82 个寄存器，对所有 82 个 D 脚记录最差建立/保持路径，另分别记录 8 个方向到每个 D 脚的最差建立路径；上述 357 对任一无路径就停止。候选文件互换、依赖表被改也会在开综合前被拒绝。**这一阶段只有逻辑证明和输入校验；三版综合估计见下节，尚无三版布线对照。** 局部实验不含 I-cache 和整机跨 SLR 布线，不代替整机检查。

```sh
python3 scripts/test-mega-f3-registered.py "$KIT" "$PROOF" "$PARENT/result.json" "$FRESH_REGISTERED" "$YOSYS"
python3 scripts/test-mega-f3-registered.py --check-prepared "$FRESH_REGISTERED"
# 有独立实现资源后再运行。Vivado 调用输入校验时需要 PATH 上的 python 3。
vivado -mode batch -source scripts/implement-mega-f3-registered.tcl -tclargs "$FRESH_REGISTERED" "$FRESH_ROUTES"
```

## 在 VCU118 同型号器件上综合后，哪些路径值得布线？

以下是 Vivado 2024.2（build 5239630）的**综合后、未布局**时序估计。三个方案使用相同的 `xcvu9p-flga2104-2L-e` 器件、5.714 ns 时钟和 638 个边界寄存器。[去敏数据](perf-mega175-f3-synthesized.json)记录了三份综合网表的指纹、全部输出组最差路径，以及逐对比较。SLR 连线、实际时钟树、预测器上游和 I-cache BRAM 均不在这个实验里。

| 写法 | 边界内 LUT | 整段最差建立余量（ns） | 八条方向 → 校正选择 / F2 清除的最差建立余量（ns） | 357 对相同端点较原版改善 / 变差 / 持平 |
|---|---:|---:|---:|---:|
| 原版 | 238 | +1.947 | +2.020 / +2.020 | — |
| 两组前缀 + 历史先比较 | 318 | +3.217 | +3.270 / +3.270 | 341 / 16 / 0 |
| 仅用有效 lane | 297 | +2.564 | +2.649 / +2.649 | 323 / 33 / 1 |

两组前缀候选比原版多用 80 个 LUT，最差建立余量增加 1.270 ns。但也有端点变慢：方向 0 到分支掩码捕获位 75 的余量减少 0.275 ns。原版、前缀、有效 lane 三版最差保持余量依次为 +0.079、+0.079、+0.077 ns。两种候选在 Vivado 中都比原版占用更多 LUT；不能把此前 ABC 的原语数当作 Vivado 面积。优先布线验证前缀候选与原版，保留有效 lane 版作对照。校正选择是决定从哪里取指的**条件**，不是最终地址。这些结果用于决定接下来布线对比的优先级，不据此修改正在运行的整机，也不能换算为 CoreMark。

每版采集 820 行：所有输入到 82 个捕获位的建立与保持，以及八条方向分别到 82 位的建立。原生两份时序报告各抽查 10 条路径，逐条核对端点、数据延迟和余量。357 个 SAT 证明有依赖的 `(方向, 捕获位)` 在每版均有时序路径；不把另外 299 对设为 false path。逐对变化用报告的 1 ps 精度计，而不是只比较几个最差值。刻意混入另一版的路径表、混入错误控制台、删掉一个目的位、反转一个必需依赖标记，审查均拒绝。

**为什么没有局部布线成绩？** 原版已写出综合网表。第一次布局因可用物理内存接近保护下限而停止；另起进程从同一份网表重试，布局器在 5 GiB 作业限制下报告 `bad allocation`。保留这三个小网表，等整机实现释放资源后做对等的布线比较，不放宽当前内存保护。OOC 的 `HD.CLK_SRC` 未设定，工具不能估计顶层时钟延迟与偏斜；556 个端口输入和 82 个端口输出没有 I/O 延迟，所有内部端点均有时钟并受到约束。没有虚设时钟位置或新增例外以改善结果。

复现时每案用全新的输出目录，保存 Vivado 完整控制台。`NAME` 可取 `stock`、`prefix_and_compare` 或 `eligible_lanes`。下面前两条只收集和审查综合估计；最后一条才从指定指纹的网表开始布局布线。若原版综合已完成而后续布局中止，可用 `measure-synth` 重新打开该网表采集估计，此时审查命令的后两个参数应指向重开后的报告目录与控制台。三案对比时给同一个审查命令传三组 `--case`。

```sh
vivado -mode batch -source scripts/implement-mega-f3-registered.tcl -tclargs "$QUALIFIED" "$SYN" "$NAME" synth > "$SYN_CONSOLE" 2>&1
python3 scripts/review-mega-f3-routes.py "$QUALIFIED" estimate --case "$NAME" "$SYN/$NAME" "$SYN_CONSOLE" "$SYN/$NAME" "$SYN_CONSOLE"
vivado -mode batch -source scripts/implement-mega-f3-registered.tcl -tclargs "$QUALIFIED" "$ROUTE" "$NAME" from-synth "$SYN/$NAME/synthesized.dcp" "$VERIFIED_SHA256"
```
