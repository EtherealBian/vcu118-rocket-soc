# 四路 BOOM：这批慢比较在发出地址以前就在等

原版单 hart 四路 BOOM、同一份严格对齐 ELF、单上下文、2,000 B。性能和验证种子各重放四轮用户态 RTL 快照。对热点 `0x13ea4: lh x6,2(x17)`，**1,667 次退休实例全部只向正常 D-cache 端口成功提交一次请求，全部命中；从地址发出到取得半字均为 2 拍**。这解释了[上一轮发现的慢比较](perf-strict-address-chain.md)：等几十拍的不是这条半字加载的缓存响应。

| 同一观察口径 | 性能种子 | 验证种子 |
| --- | ---: | ---: |
| 已匹配的 `x6` 加载；其中分支派发后超过 8 拍才收齐操作数 | 830；62 | 837；50 |
| 最长一次：分支派发 → `x6` 地址发出 → 数据就绪 | 47 + 2 拍 | 48 + 2 拍 |
| 长等待中执行前驱 `ld x17,8(x8)` 的次数 | 55 | 40 |
| 这些前驱从自身派发到发出地址，中位数 / P95 / 最大 | 13 / 39 / 48 拍 | 12 / 39 / 48 拍 |
| 长等待中跳过该前驱的次数；这些 `x6` 从自身派发到地址发出的中位数 | 7；35 拍 | 10；21 拍 |

在执行了该前驱的每个样本中，核对了它返回的整个 64 位值确实是 `x6` 加载的基址。即便专看长等待，前驱发出地址后也是 2–5 拍得到指针，随后 2–3 拍发出半字地址。跳过该前驱的样本不作这种归因。**优化决策：不因这组长等待扩大数据缓存，也不据此改 DDR。** 目前尚不能把发地址前的等待进一步断言为寄存器未就绪或调度仲裁。性能种子四轮超过 8 拍的部分逐笔相加只有 764 拍，验证种子 611 拍；乱序等待可能重叠，这不是可节省的整轮周期。作量级对照：同一 ELF 四轮的[性能窗口](perf-strict-user-replay.md)实测 653,447 模型周期，150 MHz 下四轮要达到目标的预算为 600,000 拍。优先看原版最终布线和整轮指标，不把单个热点当作达标方案。

**怎样区别命中、重试和存储转发。** 按派发沿和 ROB 槽选出真实退休的指令。观察两条 LSU → D-cache 通道，确认上一沿全局 `ready && valid` 和本通道 `valid`，下一沿为正常 LSU 类型且 S1 有效；用活跃 LDQ 项映射回同一动态票据及物理目的寄存器。S2 必须对应同一请求通道和物理地址；分别记录 `hit` 和返回的 `nack`，并区分 S1 后未进入正常 S2 的请求。最后按 LSU 实际返回多路器区分 D-cache 数据与存储队列数据，并把 `x6` 返回值对回已验证的分支轨迹。这里的 1,667 个 `x6` 结果均与同沿、同通道、无 nack 的正常 S2 命中匹配；**不把任意缓存响应或内部 MSHR 重放算成这种命中**。结论不推广到所有加载或真实板上 DDR。

[去敏统计与探针指纹](perf-strict-left-load.json)。两种种子的 PC、退休票据、重定向、事件、UART、上一代操作数和地址轨迹的散列逐项未变，干净源码重链接得到相同探针。私有逐值轨迹、用户内存与模型不发布。使用[已封存的输入](perf-strict-load-use.md)可重跑：

```sh
python3 scripts/test-strict-load-use.py "$STOCK_KIT" "$STOCK_OBJ" "$GUEST" "$PRIVATE/b2" "$PRIVATE/left" "$VERILATOR_INCLUDE" --left-load
python3 scripts/review-strict-left-load.py "$PRIVATE/left" "$ELF" > "$PRIVATE/left-review.json"
cmp "$PRIVATE/left-review.json" docs/perf-strict-left-load.json
```
