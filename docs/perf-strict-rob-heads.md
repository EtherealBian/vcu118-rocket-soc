# 哪条指令真的卡在四路 BOOM 的退休队首？

性能种子的四轮用户态 RTL 窗口内，共有 **122,447 个时钟沿没有指令退休**。其中 **116,232 拍（94.9%）**，下一条最终退休的指令已经派发，确实就在重排序缓冲区（ROB）这一行最老的有效槽，而且该槽的 `busy` 还没清。这个判断来自真实的队首状态，不是用 IPC 或下一条 PC 反推原因。[两种种子的原始计数摘要](perf-strict-rob-heads.json)。这里没有测量物理时钟、完整 Linux 耗时或板上 CoreMark。

| 同一严格对齐 ELF、单 hart、每种种子 4 轮 | 性能种子 | 验证种子 |
| --- | ---: | ---: |
| 整个热区周期（两个计时边界的模型沿号之差） | 653,447 | 657,536 |
| 两次热区退休之间，完全无退休的沿 | 122,447 | 116,025 |
| 下一条退休指令是队首，且仅 `busy` 挡住提交 | 116,232 | 109,759 |
| 队首行没有有效槽 | 6,107 | 6,131 |
| 队首有异常标志（含同时禁止提交的沿） | 108 | 135 |

“没有有效槽”只说**队首这一行**，并非整个 ROB 为空。带异常标志也不等于每拍都发生架构陷阱。这些数只覆盖零退休沿；不足四条但有退休的时钟沿没有计入。

## 指针反转循环，而不是误判最多的比较分支

- 两个种子排第一的都是链表反转循环末端的 `0x13b6a: c.bnez x14,0x13b62`。性能种子里这条分支退休 **24,480 次**，以 `busy` 状态停在最老有效槽 **27,960 拍**；只有 **8 个**退休实例有自己的后端 B2 重定向，它们合计占其中 **12 拍**。验证种子对应 **27,692 拍**、**10 个**实例、**16 拍**。因此，给这条分支换预测器，并不能由这些计数推出可以省掉近 2.8 万拍。
- 上一轮[重定向次数最多的比较分支](perf-strict-redirects.md) `0x13eda` 有 325 / 308 个带 B2 的退休实例。两种种子都**没有**一个零退休沿以它为随后退休的忙队首。这并不说明它的误判没代价：重取指损失可能体现在别的指令或不足四条退休的沿上。
- 每次 `0x13b6a` 回跳，实际执行序列是 `mv x8,x14 → ld x14,0(x8) → sd x13,0(x8) → mv x13,x8 → bnez x14`。每种种子核对了 **23,664 个**连续回跳区间，另有 **816 次**退出。性能种子里从一次分支退休到下一次的间隔合计 **99,078 拍**（占整个热区的 **15.2%**），其中 **18,305 个**区间恰好是 5 拍。验证种子对应 **98,996 拍**、**18,262 个**五拍区间。这些区间不重叠，但包含有效工作，不是可消除的周期；`busy` 也不能区分调度、等操作数和结果写回。

**工程选择：**先保留原版布局布线。如果继续做每拍吞吐优化，下一个有依据的实验是对这条五指令循环，对齐两次迭代间的指针加载结果、下一次地址生成和分支执行/清忙时刻。不要因为看到 `busy` 就增宽提交、增加缓存，或把这些拍数折算成板上分数。

## 如何复核

在[原版四路用户态重放](perf-strict-user-replay.md)上重新链接只读探针，实际 BOOM 归档和 ELF 不变。每个被观察的热区沿，用 4 个有效位、各槽真实忙位、异常、CSR 停顿和全局禁止位重建物理提交掩码，要求与四个 `io_commit_valids` 逐位相符；记录无架构退休的沿。独立以完整退休票据的沿号求补集，逐拍对应；用**派发沿号和槽号**而非循环复用的槽号，鉴别当时的队首是不是随后退休的动态指令。两个种子的有序 PC、派发/退休票据、B2、UART 和事件均与先前已锁定的证据逐字节相同。公开结果只保留聚合与指纹。边沿补集含左右两个有提交的端点，热区时长仍是端点之差，不能多算一拍。

```sh
python3 scripts/test-strict-load-use.py "$KIT" "$OBJ" "$GUEST" "$PREVIOUS_REDIRECT_CAPTURE" "$FRESH_DIR" "$VERILATOR_INCLUDE" --rob-heads
python3 scripts/review-strict-rob-heads.py "$FRESH_DIR" "$STRICT_ELF" > "$FRESH_DIR/review.json"
```
