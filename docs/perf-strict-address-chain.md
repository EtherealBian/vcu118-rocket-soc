# 四路 BOOM：链表比较的长等待来自哪一条加载？

同一严格对齐 ELF、单 hart、单上下文、2,000 字节、每种种子四轮用户态 RTL 快照。`0x13eda` 比较 `x6` 和 `x28`。上次发现 [`x28` 多数时候最后到](perf-strict-load-use.md)；这次发现**最慢的比较反而全在等 `x6`**。

| 同一条退休比较的观察沿差（拍） | 性能种子 | 验证种子 |
| --- | ---: | ---: |
| 逐项核对的 `c.ld x10,8(x13)` → `lh x28,2(x10)` → 分支 | 830 | 837 |
| 前一条加载发出地址 → 指针结果；后一条发出地址 → 半字结果（各自所有样本） | 2；2 | 2；2 |
| 指针结果 → 后一条发出地址，中位数 / P95 | 3 / 3 | 3 / 3 |
| 两条加载都由 D-cache 应答；仅指针由存储队列转发 | 830；0 | 834；3 |
| 分支派发后超过 8 拍才收齐操作数：次数 / 最长等待 | 62 / 49 拍 | 50 / 50 拍 |

**为什么以 8 拍区分？** 两种种子中，凡是 `x28` 最后到，从分支派发到收齐操作数都不超过 8 拍。超过这个实测上界的 112 个比较全是 `x6` 最后到。性能种子中 55 个、验证种子中 40 个执行了 `0x13e9e: ld x17,8(x8)` 后进入这段代码；另外分别有 7 个和 10 个从另一条路径跳过该加载。因此不能把所有长等待都归给紧邻的 `x17` 加载或 DDR。若目标是缩短长等待，应先查 `lh x6,2(x17)` 发出地址前等了多久、发出后是否重试；若只是优化常见的 `x28` 路径，应看指针结果到地址发射的调度间隔，而非先改存储转发或缓存容量。两者都须以相同 ELF 的整轮周期验证收益，本次没有修改处理器或提高板分。

**如何测。** 按派发沿和 ROB 槽锁定退休实例，在两路地址生成单元向 LSU 发出的有效请求上读取源寄存器、有效地址、物理目的寄存器和加载队列索引；在整数加载结果上读取同一笔的返回值。逐次核对指针结果等于后一条的完整基址、地址等于基址加 2、队列和目的寄存器匹配；再把半字结果逐位对回原分支探针。按 LSU 结果多路器**实际选择**区分 D-cache 与存储队列。D-cache 应答不等于已证明 L1 命中，也不能拿两拍推算 DDR 延迟。

两次运行原来的 PC、票据、重定向、事件、UART 及加载到分支的值轨迹逐字节散列均未变。对真实观测同时改写基址和有效地址，或者仅改加载队列索引，检查均拒绝。干净源重新链接的探针与运行版本相同。[去敏统计和散列](perf-strict-address-chain.json)；逐值轨迹、模型、ELF 和 RAM 不公开。复核可沿用[原探针的输入](perf-strict-load-use.md)：

```sh
python3 scripts/test-strict-load-use.py "$STOCK_KIT" "$STOCK_OBJ" "$GUEST" "$PRIVATE/b2" "$PRIVATE/addr" "$VERILATOR_INCLUDE" --address-chain
python3 scripts/review-strict-address-chain.py "$PRIVATE/addr" "$ELF" > "$PRIVATE/address-review.json"
cmp "$PRIVATE/address-review.json" docs/perf-strict-address-chain.json
```
