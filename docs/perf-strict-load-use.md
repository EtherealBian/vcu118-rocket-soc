# 四路 BOOM：链表比较的两个数什么时候到？

`core_bench_list` 中，`0x13eda` 比较 `x6` 和 `x28`，决定接下来取哪一个链表节点。上一次[分支重定向实验](perf-strict-redirects.md)只看到分支预测错后何时恢复。这次沿同一份严格对齐 ELF 的实际退休路径，找到每次比较的两条半字加载，并在 BOOM 的整数加载结果端和分支 ALU 输入端逐次比对完整 64 位数值。

| 单 hart 四路原版；同一用户态快照各四轮 | 性能种子 | 验证种子 |
| --- | ---: | ---: |
| 逐项核对通过的退休比较；其中有 B2 的次数 | 830；325 | 837；308 |
| 分支派发 → 较晚一个加载结果，P50 / P95（拍） | 5 / 14 | 5 / 9 |
| 较晚加载结果 → 分支 ALU 收到两个操作数，2 拍 / 3 拍的次数 | 826 / 4 | 836 / 1 |
| 最后到的是 `x6` / `x28` 的次数 | 154 / 676 | 121 / 716 |
| 从 ALU 输入到注册 B1 的最小 / 最大间隔（拍） | 1 / 1 | 1 / 1 |

**如何取舍。** 两种种子中，每条已退休的热点比较在派发时都还没有收到两个加载的最后一个结果。性能种子的 325 次后端重定向中，有 280 次是 `x28` 对应的加载最后到。先检查 `x28` 的基址指针加载、两路访存的发射顺序和旁路，再决定是否改调度；暂不为这一个热点改预测器或增加一级流水。即使缩短一条依赖，也得重新跑同一 ELF 检查整轮周期，因为其他指令可能在同一时段并行执行。

[后续地址生成实测](perf-strict-address-chain.md)已区分常见的 `x28` 路径与较少但更慢的 `x6` 等待。

**怎样核对。**

- 先校验原版五份捕获（有序 PC、动态 ROB 票据、重定向、事件与 UART）的散列。以 `(派发沿, ROB 槽)` 选择两条加载和分支的每个退休实例。新观测不改 RTL、新捕获的五份散列必须逐项与原版相同。两种种子中，从 `lh x6,2(x17)` 到分支的每一段都与 ELF 的连续 15 条机器指令完全一致；`lh x28,2(x10)` 是第 3 条，没有其他指令在这段内改写比较操作数。不能把这个连续区间再往前推：两种种子各有 32 次从另一条路径直达 `0x13ea2`，跳过了前面的 `x17` 指针加载。
- 读取两路 LSU 的整数加载结果。第 0 路仅在内存执行单元 `valid` 时取共享写回仲裁器的输出，此时其输入 0 优先；第 1 路的执行单元直通 LSU 数据。核对加载结果已按有符号半字扩展、两条加载物理目的寄存器不同、读数逐比特等于发给该分支 ALU 的两个源操作数。这里能看到整数加载结果，不能区分是 D-cache 响应还是存储转发，更不是 DDR 芯片的延迟。
- 从同一 ALU 通道核对下一拍注册的 B1、完整源 PC、实际有符号比较方向以及下一条退休 PC；有 B2 的还核对再下一拍的重定向。每种种子分别在真实捕获副本上翻转一个加载值的最低位、平移一个 B1 观察沿，复核均须拒绝。干净源重新链接的探针可执行文件与实际运行的文件逐字节相同。
- 表中“拍”是同一整核功能模型的观察沿差，分位数采用最近秩。加载结果到 ALU 输入的间隔不是可直接节省的拍数。这里只测了用户态快照的一个热点，没有测板上 Linux 的每秒迭代数，也没有据此认定全机九级或判断 175 MHz 时序收敛。
