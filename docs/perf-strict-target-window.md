# 24,000 轮到底要执行多少条指令？

在待上板的同一份 Linux ELF 上，**性能种子 24,000 轮共执行 8,084,760,119 条计时窗口内的用户指令**。不再用四轮数据外推全程。这是 Linux 用户态模拟的工作量，不是 BOOM 的周期或板测成绩。

| 固定 RV64GC ELF，2,000 字节，一个上下文 | 性能种子 | 验证种子 |
|---|---:|---:|
| 24,000 轮的用户指令数 | 8,084,760,119 | 8,094,820,378 |
| 平均指令/轮 | 336,865.005 | 337,284.182 |
| 最少 / 最多指令的一轮 | 336,601 / 337,140 | 336,978 / 337,577 |
| 完整运行的最终 CRC | `0x4983` | `0xeb93` |

**频率与吞吐的关系。** 如果板上 CPU 确实运行在 175 MHz，1,000 次/秒给每轮 175,000 拍；仅就性能种子的用户指令，就要在全部墙钟周期中平均完成 **1.92494 条/拍**。若是 150 MHz，则要 **2.24577 条/拍**。中断、内核工作等会进一步压缩可用于这些指令的周期。这里不把目标时钟当作已签核时钟，也不把[四轮 RTL 模型的周期](perf-strict-user-replay.md)乘成全程成绩。

**优化靶点仍在。** 对[已有 RTL 证据的链表反转热循环](perf-strict-reversal.md)，两种种子各自全程都实际执行了 **141,984,000** 次 `c.mv x8,x14` 和 **146,880,000** 次 `c.ld x14,0(x8)`（每轮平均 5,916 和 6,120 次）。入口跳转跳过复制，不能将每次加载都算作一次复制机会。该复制的出现次数也不是[候选重命名逻辑](perf-copy-load-rename.md)的实际命中数；能否同拍译码、能省几拍，要看同一整核 A/B。

四轮与全程的按 PC 指令频率分布接近，但不完全相同：两种种子全程分别有 3,927、3,426 条动态指令落在各自四轮从未执行过的 PC 上。仅能说四轮覆盖了绝大部分指令工作量，不能推论时间、缓存或分支预测行为也相同。[完整汇总、分轮序列与 PC 计数指纹](perf-strict-target-window.json)。

## 复核方法

1. Linux x86-64，从 Ubuntu 源包 `qemu_4.2.orig.tar.xz` 私下构建只模拟 RV64 Linux 用户态的 QEMU 4.2.0，打开 TCG 插件。脚本核对源包、插件头及原始 ELF 的 SHA-256；不安装系统包，不改 ELF 或 CPU RTL。需 C 工具链、glib 开发文件、Python、make，以及该工程的 RISC-V objdump。
2. 对每个种子和长度跑两次：一遍按每条指令插入计数，一遍按翻译块内连续区段首条计数。区段在计时调用/返回、轮回边和链表入口处切开。每轮须有两次链表调用；两种计数法须给出完全相同的逐轮数组及每个 PC 的次数，而不只是相同总数。用反汇编核对所有计入的 PC。`ordered_round_counts_sha256` 对逐轮计数以小端 64 位编码；`pc_histogram_sha256` 对按 PC 排序的 `(小端32位PC, 小端64位次数)` 求散列。
3. 短运行额外生成有序 PC 流，必须与[独立发行版 QEMU 的四轮记录](perf-strict-user-window.json)逐种子 SHA-256、分轮及分类计数一致。长运行不保存数十亿条 PC 的轨迹，不宣称比对了全程顺序。两种长度均检查种子、三项内核 CRC、最终 CRC、上下文、数据大小、轮数和编译标识。模拟太快导致的上游时长错误只允许用于核对工作量；不接受其速率为成绩。

```sh
python3 scripts/count-target-user-window.py "$QEMU_SOURCE_ARCHIVE" \
  "$RELEASE/coremark-g15-gc-lto-ooo-strict.elf" "$RISCV_OBJDUMP" > /tmp/strict-target-window.json
diff -u docs/perf-strict-target-window.json /tmp/strict-target-window.json
```
